# Tuning run output specification

This document describes the files and standard output produced by `make tune`
and `make tune-short`.

## Directory layout

Each run creates a timestamped directory under `tools/runs/<solver_commit>/`:

```
tools/runs/<solver_commit>/
├── latest -> run_<YYYYMMDD_HHMMSS>          # symlink to the most recent run
└── run_<YYYYMMDD_HHMMSS>/
    ├── best_config.toml                     # best [scorer] config found
    ├── best_summary.json                    # metadata for the best config
    └── history.json                         # per-generation CMA-ES log
```

- `<solver_commit>` is the short git commit of the checked-out `atomic_solver`.
- `latest` is updated to point to the new run after it finishes successfully.
- Previous runs are preserved, so you can compare them or resume from any
  `history.json`.

## Standard output

While a run is in progress, `tools/tune.py` prints one line per generation:

```
gen=<n> evals=<total_evals> best=<best_f> mean=<mean_f> sigma=<sigma> \
  ok=<total_ok> wrong=<total_wrong> timeouts=<total_timeouts> \
  total_child=<total_child_evals> t=<elapsed_seconds>s
```

Fields:

| Field         | Meaning                                                                   |
| ------------- | ------------------------------------------------------------------------- |
| `gen`         | Generation number (1, 2, ...).                                            |
| `evals`       | Total benchmark evaluations completed so far.                             |
| `best`        | Best scalar loss (`best_f`) found so far; lower is better.                |
| `mean`        | Average loss of the candidates evaluated in this generation.              |
| `sigma`       | Current CMA-ES step size in log-space.                                    |
| `ok`          | Total positions across the generation that returned the expected outcome. |
| `wrong`       | Total positions across the generation that returned a wrong outcome.      |
| `timeouts`    | Total positions across the generation that timed out.                     |
| `total_child` | Sum of `child_evals` across all candidates in the generation.             |
| `t`           | Wall-clock time for the generation.                                       |

At startup the following header lines are printed:

```
CMA-ES n=<dims> lambda=<pop_size> mu=<parents> max_evals=<max_evals>
output_dir=<run_directory>
baseline=<baseline_file> suite=<suite> timeout=<seconds> workers=<workers>
resume=<history_file> source=<history|summary> start_f=<loss> start_sigma=<sigma>
```

The `resume` line is omitted when starting from scratch or from `--seed-config`.

On a normal exit:

```
Done. Best config written to <run_directory>/best_config.toml
```

## `best_config.toml`

A partial TOML config that can be passed directly to the benchmark binary via
`--config`:

```toml
# Generated by CMA-ES tuner
[scorer]
score_capture = 3508
score_threat_last = 9695
...
score_winning_capture = 100000000

[scorer.pieces]
pawn = 100
knight = 320
...
```

Only the parameters being tuned are written; `atomic_solver` uses
`#[serde(default)]` to fill in any missing fields. The fixed thresholds
`score_promotion` and `score_winning_capture` are included for clarity.

## `best_summary.json`

JSON document describing the best candidate found during the run.

Schema:

```json
{
  "best_f": 15.615526471708344,          // best scalar loss seen
  "best_x": [ -0.354, ... ],             // latent vector for best_f
  "sigma": 0.12874831679810692,          // CMA-ES step size at end of run
  "evals": 240,                          // total benchmark evaluations
  "params": {                            // decoded ScorerParams
    "score_capture": 3508,
    "capture_net_scale": 10,
    ...
  },
  "info": {                              // benchmark details for the best candidate
    "wrong": 0,
    "timeout": 0,
    "ok": 23,
    "efficiency": 22.47609264876091,    // sum of child_evals / baseline per position
    "returncode": 0,
    "total_child_evals": 18821027
  }
}
```

- `best_f` is the scalar loss used by CMA-ES; lower is better.
- `best_x` is the raw latent vector and can be used to warm-start another run.
- `info.total_child_evals` is the absolute work done for the best candidate on
  the training suite; it is the primary external metric.
- `info.efficiency` is the sum of per-position `child_evals / baseline` ratios.

## `history.json`

A JSON array with one entry per generation:

```json
[
  {
    "generation": 1,
    "counteval": 12,
    "sigma": 0.28590047418897774,
    "best_f": 15.897390851315292,
    "best_x": [ ... ],
    "mean_f": 21.52796793116283,
    "details": [
      {
        "wrong": 0,
        "timeout": 1,
        "ok": 22,
        "efficiency": 26.44007650499187,
        "returncode": 0,
        "total_child_evals": 40859591
      },
      ... // one element per candidate in the generation
    ]
  },
  ...
]
```

- `best_f` and `best_x` are the global best at the end of that generation.
- `mean_f` is the average loss of the candidates in that generation.
- `details[i]` corresponds to the i-th candidate of the generation and contains
  the same fields as `info` in `best_summary.json`.

`history.json` is used by the `--resume` feature to warm-start CMA-ES from the
previous best latent vector and `sigma`.

## Validation output

`make validate-quick` and `make validate-thorough` invoke the benchmark binary
with the tuned `best_config.toml` and print the benchmark JSON to stdout. They
do not write a file by default; redirect or pipe the output if you want to keep
it. The JSON schema is documented in
`atomic_solver/docs/spec/optimizer_interface.md`.

## Comparing multiple runs

`make compare` reads every `run_<timestamp>/best_summary.json` under
`tools/runs/<solver_commit>/`, compares each run's `total_child_evals` to the
matching `baseline_quick_<commit>.json`, and shows the improvement from one run
to the next. The columns are:

```
run       evals  best_f    child_evals  vs_base%  vs_prev%  wrong  to
run_...   240    15.6155   18,821,027   +21.02              0      0
```

- `vs_base%`: percent reduction in `total_child_evals` versus the baseline.
- `vs_prev%`: percent reduction versus the previous `run_*` directory.
- Positive numbers mean fewer `child_evals` (better); negative means the run
  regressed.

## Promoting a config for version control

`tools/runs/` and `baseline_quick_*.json` are ignored by git because they are
generated artifacts. If you want to commit a tuned config, run:

```bash
make promote
```

This copies `tools/runs/<commit>/latest/best_config.toml` to
`best/best_config_<commit>.toml`, which you can then `git add` and commit. The
filename includes the solver commit so it is clear which version of
`atomic_solver` it belongs to.

## Cross-platform notes

The benchmark binary (`atomic_solver/target/release/examples/benchmark`) is
platform-specific. If you switch host OS or architecture, run
`make distclean && make build` before tuning or validating. The generated
`baseline_quick_<commit>.json` and the `child_evals` values in the run output are
deterministic for a given solver version, so they are portable and comparable
once the binary is rebuilt.
